Variables

Lesson 4 · g8 bytecode compiler · Prev: The Accumulator Model · Reference: Instruction Set

Until now your registers have been anonymous temporaries — the compiler allocates r0, r1, uses them once, and forgets them. That changes with variables. A variable is just a register with a name.

The new grammar

Your language goes from a single expression to a program — a sequence of let bindings followed by a final expression: 

Program  := Stmt* Expr
Stmt     := 'let' Ident '=' Expr
Expr     := Res Op Res
Res      := '(' Expr ')' | Ident | Digit
Op       := '+' | '*'

A program looks like this:

let x = 10
let y = 20 + x
x * y

Three new things: the let keyword, identifiers (x, y), and the = sign. The final expression is the program's result.

What changes in each layer

Lexer

Three new token kinds:

TokenExample
LETlet
IDENTx, foo, myVar
ASSIGN=

Identifiers are sequences of letters (and underscores, digits after the first character — your call how strict). The lexer needs to distinguish let (keyword) from other identifiers. Simplest approach: lex all letter-sequences as IDENT, then check if the string is "let" and swap the kind.

AST

Two new node types:

// A let-binding: let x = <expr>
type LetStmt struct {
    Name  string
    Value *AST
}

// A variable reference: x
// Add a Name field to AST, or use a new node type

The simplest change to your existing AST struct: add a Name *string field. A leaf node is either an integer (Value != nil) or a variable reference (Name != nil). And the program becomes a list of let-statements plus a final expression.

Parser

The parser now handles a program (sequence of statements, then a final expression) rather than a single expression. parseRes gains a new case: when it sees an IDENT token, it returns a variable-reference AST node.

Compiler — the interesting part

This is where variables meet registers. The compiler maintains a symbol table: a map from variable name to register index. 

type Compiler struct {
    code    []byte
    cons    []int
    nextReg int
    symbols map[string]int  // variable name → register index
}

When the compiler sees let x = 10 + 20:

  1. Compile the right-hand expression (10 + 20) — result lands in the accumulator
  2. Allocate a register for x
  3. Emit Star rN — store the accumulator into x's register
  4. Record symbols["x"] = N

When the compiler later sees x used in an expression:

  1. Look up "x" in the symbol table → register rN
  2. Emit Ldar rN — load the variable's value into the accumulator

This is where Ldar earns its place. It's the instruction that reads a named variable. Every variable reference in source code becomes an Ldar in bytecode.

Worked example

Source:

let x = 10
let y = 20 + x
x * y

Compilation trace:

// let x = 10
LdaSmi [0]        // acc = constants[0] = 10
Star   r0         // r0 = 10, symbols["x"] = r0

// let y = 20 + x
LdaSmi [1]        // acc = constants[1] = 20
Star   r1         // r1 = 20 (temp stash for +)
Ldar   r0         // acc = r0 = 10 (load x)
Add    r1         // acc = r1 + acc = 20 + 10 = 30
Star   r2         // r2 = 30, symbols["y"] = r2

// x * y (final expression)
Ldar   r0         // acc = r0 = 10 (load x)
Star   r3         // r3 = 10 (temp stash for *)
Ldar   r2         // acc = r2 = 30 (load y)
Mul    r3         // acc = r3 * acc = 10 * 30 = 300

Constants: [10, 20]

Registers

Variables vs temporaries

Look at the register file after execution. Some registers hold variables — values that have names and might be read again. Others hold temporaries — intermediate values the compiler stashed during a binary operation.

RegisterContentsRole
r010Variable x — read twice later
r120Temporary — stash for + in 20 + x
r230Variable y — read once later
r310Temporary — stash for * in x * y

In V8, this distinction matters. Temporaries can be reused aggressively. Variable registers must stay alive as long as the variable is in scope. A real register allocator distinguishes the two; your linear allocator doesn't need to yet.

How V8 does it

In V8, local variables are register slots. When Ignition compiles a function, it counts the locals and allocates that many registers at the bottom of the register file. Temporaries go above them. The frame layout looks like: 

Register file for a function:
  r0  → parameter 0 (or local 0)
  r1  → parameter 1 (or local 1)
  ...
  rN  → last local
  rN+1 → first temporary
  rN+2 → second temporary
  ...

Variables that escape their scope (captured by closures, used across eval) go into a context object on the heap instead — loaded with LdaContextSlot and stored with StaContextSlot. But simple locals stay in registers, which is the fast path.

Your VM is now doing the same thing V8 does for simple locals. A let binding allocates a register. A variable reference emits Ldar. The symbol table is your scope. This is the foundation that everything else builds on — functions, closures, and control flow all rely on this mapping of names to registers.

Now implement it

This is the biggest change to your codebase so far. Take it in order:

  1. Lexer: Add LET, IDENT (with a Name string field on Symbol), and ASSIGN tokens. Handle the keyword check.
  2. AST: Add a Name *string field for variable references. Add a LetStmt struct (or a separate AST node kind). Add a ProgramAST that holds a list of lets plus a final expression.
  3. Parser: Add parseProgram (loops over let-statements, then parses the final expression). Update parseRes to handle IDENT tokens.
  4. Compiler: Add a symbols map[string]int. For let, compile the value, allocate a register, emit Star, record the mapping. For variable references, look up the name, emit Ldar.
  5. VM: Add the Ldar handler (it's one line — you already have the opcode defined).

Test the end-to-end pipeline with let x = 10; let y = 20 + x; x * y → 300. Your disassembler will be especially useful here — print the bytecode and verify each instruction makes sense.

What's next

With variables, your language can express real computations. The next frontiers:

  • Control flow — if/else, which introduces jump instructions and the concept of basic blocks
  • Functions — call frames, each with their own register file, and the return instruction
  • V8 embedding — hooking your compiled bytecode into a real V8 isolate
