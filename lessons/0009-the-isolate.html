The Isolate

Lesson 9 · ~25 min · Prerequisite: Lesson 8

You have all the pieces: a register VM with an accumulator, a heap with tagged values, and a mark-compact garbage collector. This lesson assembles them into an Isolate — a self-contained execution context with its own memory, its own GC, and no shared state with any other Isolate.

This is the core abstraction of V8. Every Chrome tab, every Node.js worker, every Cloudflare Worker runs inside an Isolate. They share a process but nothing else.

What Is an Isolate?

An Isolate is everything needed to run a program, bundled into one struct:

pub struct Isolate {
    acc: Value,                 // accumulator
    heap: Heap,                 // object storage + GC
    gc_threshold: usize,        // collection policy
}

That’s it. Your current VM struct is an Isolate — it already owns the heap and execution state. The lesson is about what this means when you have more than one.

One Process, Many Worlds

Two Isolates in the same process see completely separate realities: 

let mut iso_a = Isolate::new();
let mut iso_b = Isolate::new();

iso_a.eval("let name = \"alice\";");
iso_b.eval("let name = \"bob\";");

// iso_a.heap: offset 0 → "alice"
// iso_b.heap: offset 0 → "bob"
//
// Same heap offset, different bytes.
// No shared mutable state. No locks. No coordination.

Each Isolate has its own:

  • Heap (its own Vec<u8>)
  • Accumulator and execution state
  • GC (operates only on its own heap)
  • Constant pools

A tagged value with bit 0 = 1 means “heap offset X in my heap.” Passing that value to another Isolate is meaningless — it would index into a different byte array and read garbage. This isn’t a bug; it’s the isolation guarantee.

Isolate A stores a string at heap offset 0. You copy that tagged Value to Isolate B. What happens when B tries to read it?
B reads the same string — heap offset 0 is universal
B gets an error — Isolates reject foreign Values
B reads whatever is at offset 0 in its own heap — likely wrong data or a crash
The GC automatically copies the string to B’s heap

The Lifecycle

In V8, an Isolate’s lifecycle is:

  1. Create: allocate the heap, initialize state
  2. Compile: parse source → emit bytecode, allocating string constants on this Isolate’s heap
  3. Execute: run the bytecode, allocating runtime objects on this Isolate’s heap
  4. Read result: extract the final value
  5. Dispose: drop the entire Isolate — heap and all — in one shot

Step 5 is where Rust shines. When the Isolate is dropped, it owns its Heap, which owns its Vec<u8>. Rust drops the whole thing automatically. No leak, no dangling pointers, no GC needed for the Isolate itself. 

{
    let mut iso = Isolate::new();
    iso.eval("let x = \"hello\" + \" world\";");
} // iso dropped here — heap, constants, everything freed

Design: What the Isolate Owns

The Isolate wraps compilation and execution. Source code goes in, a result comes out. The caller never touches the heap or bytecode directly: 

pub struct Isolate {
    acc: Value,
    heap: Heap,
    gc_threshold: usize,
}

impl Isolate {
    pub fn new() -> Self {
        Isolate {
            acc: Value::default(),
            heap: Heap::new(),
            gc_threshold: 1024,
        }
    }

    pub fn eval(&mut self, source: &str) -> IsolateResult {
        let tokens = Lexer::lex(source);
        let stmts = Parser::new(tokens).parse();
        let mut program = Program::new();
        program.compile(&stmts, &mut self.heap);
        self.run(&program)
    }

    fn run(&mut self, program: &Program) -> IsolateResult {
        // your current fde logic, using self.heap, self.acc
        // ...
    }

    pub fn format_result(&self) -> String {
        // format self.acc using self.heap
    }
}

The key design principle: the Isolate is the boundary. Nothing goes in except source code (a &str). Nothing comes out except a formatted result or a copied primitive. Heap pointers never escape.

V8 comparison: V8’s Isolate::New() creates a new Isolate. v8::Script::Compile() compiles source within an Isolate’s context. script->Run() executes it. Results are v8::Local<v8::Value> handles that are scoped to the Isolate — you must copy data out (e.g., convert a V8 string to a C++ std::string) before the Isolate can be disposed. Your format_result serves the same purpose.

Thread Safety

In V8, a single Isolate is single-threaded. You can have many Isolates in one process (on different threads), but each Isolate is only accessed by one thread at a time. V8 has a Locker API to enforce this.

In Rust, this falls out naturally. Your Isolate takes &mut self for eval, which means only one caller can use it at a time. If you put Isolates in separate threads, each thread owns its Isolate — no Arc, no Mutex, no synchronization needed. 

use std::thread;

let handle_a = thread::spawn(|| {
    let mut iso = Isolate::new();
    iso.eval("let x = 1 + 2;")
});

let handle_b = thread::spawn(|| {
    let mut iso = Isolate::new();
    iso.eval("let x = 3 + 4;")
});

// Two threads, two Isolates, zero shared state.
If Isolate A triggers garbage collection, what happens to Isolate B?
B pauses until A’s GC finishes (stop-the-world is global)
Nothing — A’s GC only touches A’s heap and roots
B’s heap is also compacted to stay in sync
B receives A’s remap to update any shared pointers

Implementation

Step 1: Rename and refactor

Your current VM struct already is an Isolate — it owns the heap, the accumulator, and the GC threshold. Rename it: 

// vm.rs → isolate.rs (or just rename the struct)
pub struct Isolate {
    acc: Value,
    heap: Heap,
    gc_threshold: usize,
}

Step 2: Add eval

Move the lex → parse → compile → run pipeline into the Isolate. The Isolate’s heap is used during compilation (for string constants) and during execution (for runtime allocations): 

pub fn eval(&mut self, source: &str) -> Value {
    let tokens = Lexer::lex(source);
    let stmts = Parser::new(tokens).parse();
    let mut program = Program::new();
    program.compile(&stmts, &mut self.heap);
    self.run(&program)
}

fn run(&mut self, program: &Program) -> Value {
    // your existing fde() body, moved here
}

Step 3: Add read_result

The result needs to be extracted before the Isolate is dropped, because heap pointers are meaningless outside: 

pub fn read_result(&self) -> String {
    if self.acc.is_smi() {
        self.acc.as_smi().to_string()
    } else {
        self.heap.read_string(self.acc).to_string()
    }
}

Step 4: Update main.rs

fn main() {
    let src = fs::read_to_string(&args[1]).unwrap();
    let mut isolate = Isolate::new();
    isolate.eval(&src);
    println!("{}", isolate.read_result());
}

Step 5: Multi-Isolate test

This is the payoff — prove that two Isolates are independent:

#[test]
fn two_isolates_are_independent() {
    let mut iso_a = Isolate::new();
    let mut iso_b = Isolate::new();

    iso_a.eval("let x = 10 + 20;");
    iso_b.eval("let x = 99;");

    assert_eq!(iso_a.read_result(), "30");
    assert_eq!(iso_b.read_result(), "99");
}

#[test]
fn isolate_string_isolation() {
    let mut iso_a = Isolate::new();
    let mut iso_b = Isolate::new();

    iso_a.eval("let s = \"hello\";");
    iso_b.eval("let s = \"world\";");

    assert_eq!(iso_a.read_result(), "hello");
    assert_eq!(iso_b.read_result(), "world");
    // Both heaps have a string at offset 0, but different content.
}

What Comes Next

You now have a working Isolate — an independent execution context with its own heap, GC, and bytecode execution. This is the foundation that everything else builds on:

  • Contexts: V8 supports multiple Contexts within one Isolate (separate global objects sharing the same heap). This is how Chrome runs multiple iframes in one Isolate.
  • Builtins: Each Isolate has built-in functions (console.log, Math.floor). These are native functions registered on the Isolate.
  • Loops: while and for loops — same backpatching technique as if/else, but jumping backwards.
  • Objects and Maps: Heap-allocated objects with named properties — the next major heap type after strings.
Primary source: The V8 embedding guide covers the Isolate API from the embedder’s perspective — how Chrome and Node.js create and manage Isolates. For the internal structure, see src/execution/isolate.h in the V8 source — the Isolate class owns the heap, the builtins table, the thread-local state, and the GC.
