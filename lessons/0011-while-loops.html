While Loops & Variable Reassignment

Lesson 11 · ~30 min · Prev: Lesson 10 · Reference: Instruction Set

Your VM can branch with if/else, but it can’t loop. The jump instructions from Lesson 6 only move pc forward — they skip over code. A loop needs to go backward to re-test its condition. This lesson adds one new bytecode (JumpLoop), one new statement type (while), and variable reassignment (x = x + 1) — because a loop without mutation runs forever or not at all.

The Problem: Forward-Only Jumps

Look at the current Jump handler: 

ByteCode::Jump => {
    let offset = self.read_byte(&call_stack, fi);
    call_stack.frames[fi].pc += offset as usize + 1;  // always adds
}

This always adds to pc. There is no way to subtract. An if statement only needs forward jumps — it skips over the then-branch or the else-branch. But a while loop needs the instruction pointer to circle back: 

     ┌──────────────────────────┐
     │    condition test         │ ◄─── back edge
     │    JumpIfFalse ──────────┼──► exit
     │    body...                │
     │    JumpLoop ─────────────┘
     │
     ▼ (exit)
     next statement

The jump from the bottom of the body back to the condition is called the back edge. In V8’s Ignition interpreter, this is the JumpLoop bytecode — the only instruction that moves pc backward.

Why can’t we implement while with the existing Jump and JumpIfFalse instructions?
Jump can only be used inside if statements
JumpIfFalse doesn’t support loop conditions
Both only move pc forward — loops need backward jumps
The VM doesn’t support conditions inside loops

The New Bytecode: JumpLoop

JumpLoop is a backward jump. It reads an offset byte and subtracts from pc instead of adding: 

ByteCode::JumpLoop => {
    let offset = self.read_byte(&call_stack, fi);
    call_stack.frames[fi].pc += 1;     // advance past the operand byte
    call_stack.frames[fi].pc -= offset as usize;  // jump backward
}

After reading the operand, pc points to the byte after JumpLoop. Subtracting offset lands it back on the first byte of the condition.

Why not reuse Jump with signed offsets?

You could make Jump take a signed i8 and handle both directions. V8 doesn’t, for two reasons:

  1. Back edges are semantically special. They’re where the runtime checks for stack overflow, GC safe points, debugger breakpoints, and whether to tier up to the optimizing compiler. A unified Jump would need “am I going backward?” on every jump.
  2. Range. A u8 offset gives 0–255 range in one direction. A signed i8 gives only −128 to +127 each way. Separate opcodes double the effective range.
V8 parallel: V8’s JumpLoop takes two operands: a feedback slot (for profiling how often the loop runs) and the offset. The feedback slot feeds into TurboFan’s optimization decisions. Our JumpLoop takes just the offset — no profiling yet.

Variable Reassignment

A loop like while (x > 0) { x = x - 1; } needs to update x each iteration. Currently, your VM can declare variables (let x = 10;) but not reassign them (x = 5;). The parser sees x = ... and doesn’t know how to handle it — it’s neither a declaration (no let) nor an expression statement.

AST

Add a new statement variant:

pub enum Stmt {
    // ... existing variants ...
    Assign {
        name: String,
        value: Expr,
    },
}

Parser: 1-token lookahead

When the parser sees an identifier, it peeks at the next token. If it’s = (not ==), this is an assignment: 

fn parse_expr_stmt(&mut self) -> Stmt {
    if self.peek() == SymbolKind::Ident {
        if self.pos + 1 < self.syms.len()
            && self.syms[self.pos + 1].kind == SymbolKind::Assign
        {
            let name = self.pop().str_val;
            self.expect(SymbolKind::Assign);
            let value = self.parse_expr();
            self.expect(SymbolKind::Semi);
            return Stmt::Assign { name, value };
        }
    }
    let expr = self.parse_expr();
    self.expect(SymbolKind::Semi);
    Stmt::ExprStmt(expr)
}

Compiler: no new register needed

This is the elegant part. let x = 10; allocated register r0 for x and stored "x" → 0 in the symbol table. A later x = 5; compiles the right-hand side, then stores the result back into r0 using the same mapping: 

Stmt::Assign { name, value } => {
    self.compile_expr(value, heap);
    let reg = self.symbols[name];  // reuse the existing register
    self.code.push(ByteCode::Star as u8);
    self.code.push(reg as u8);
}

No new bytecode. No new register. It’s just Star rN again, targeting the same slot that the let originally created.

After let x = 10; places x in register r0, how does x = x + 1; update it?
Allocates a new register r1 and copies the value
Compiles x + 1, then emits Star r0 — same register
Uses a special Mutate bytecode
Modifies the constant pool entry for x

Compiling While Loops

Lexer and AST

Add While to SymbolKind and recognize the keyword "while" in the lexer. Add a new AST variant: 

Stmt::While {
    condition: Expr,
    body: Vec<Stmt>,
}

Parser

fn parse_while(&mut self) -> Stmt {
    self.expect(SymbolKind::While);
    self.expect(SymbolKind::LPar);
    let condition = self.parse_expr();
    self.expect(SymbolKind::RPar);
    self.expect(SymbolKind::LBrace);
    let mut body = Vec::new();
    while self.peek() != SymbolKind::RBrace {
        body.push(self.parse_stmt());
    }
    self.expect(SymbolKind::RBrace);
    Stmt::While { condition, body }
}

Compiler: the loop compilation pattern

This is the core of the lesson. The compiler emits code in five steps:

Stmt::While { condition, body } => {
    // 1. Record where the condition starts (JumpLoop target)
    let loop_start = self.code.len();

    // 2. Compile the condition (leaves 0 or 1 in acc)
    self.compile_expr(condition, heap);

    // 3. Emit JumpIfFalse with placeholder (exit the loop)
    let exit_jump = self.emit_jump(ByteCode::JumpIfFalse);

    // 4. Compile the body
    self.compile_stmts(body, heap);

    // 5. Emit JumpLoop back to loop_start
    let offset = self.code.len() + 2 - loop_start;
    self.code.push(ByteCode::JumpLoop as u8);
    self.code.push(offset as u8);

    // 6. Patch the exit jump to land here
    self.patch_jump(exit_jump);
}

Steps 1–4 mirror if compilation exactly. Step 5 is new: instead of falling through, the compiler emits JumpLoop to circle back to the condition. Step 6 patches the exit jump to skip past the JumpLoop.

The Offset Calculation

Getting the JumpLoop offset right is the hardest part of this lesson. Let’s trace through it carefully: 

loop_start = 0          // condition starts at byte 0

... condition occupies bytes 0..7 ...
... JumpIfFalse at bytes 8,9 ...
... body occupies bytes 10..19 ...

// Now we emit JumpLoop:
// code.len() == 20   (where the opcode goes)
// After VM reads the operand: pc == 22
// We want: pc - offset == loop_start == 0
// So: offset == 22 == code.len() + 2 - loop_start

self.code.push(JumpLoop);   // byte 20
self.code.push(22);          // byte 21
// VM: pc = 22, then pc -= 22, pc = 0  ✓

The +2 accounts for the two bytes of the JumpLoop instruction itself (opcode + operand). If you forget it, the loop lands on byte 2 instead of byte 0, skipping the first instruction of the condition on every iteration.

Common bug: Using self.code.len() - loop_start without the +2. This makes the loop jump two bytes too late. The symptom is subtle: the loop appears to work for some programs but silently skips the first comparison operand, producing wrong results or infinite loops.
Why does the JumpLoop offset formula include + 2?
The JumpLoop instruction is 2 bytes — pc advances past both before jumping
The condition always starts 2 bytes into the loop
We need to skip over the JumpIfFalse instruction
It compensates for the operand being unsigned

Source:

let x = 3;

    x = x - 1;

x;

Recursion vs. Iteration

Before this lesson, computing a sum required recursion: 

// BEFORE: recursion (only option)
function sum(n) {
    if (n < 1) { return 0; }
    return n + sum(n - 1);
}
sum(100);

This pushes 100 frames onto the CallStack, each with its own register window. After adding while and reassignment: 

// AFTER: iteration
let total = 0;
let i = 100;
while (i > 0) {
    total = total + i;
    i = i - 1;
}
total;

One frame. A few registers. No stack growth. No GC pressure.

Why does the iterative version use constant memory regardless of input size?
The VM pre-allocates memory for all iterations
The GC collects memory between iterations
Each iteration reuses the same frame and registers — no stack growth
The compiler unrolls the loop into straight-line code

How V8 Compiles While Loops

V8’s Ignition bytecode for the same pattern: 

// V8: while (x > 0) { x = x - 1; }
   0: Ldar a0
   2: Star r0
   4: LdaZero
   5: TestGreaterThan r0, [0]
   7: JumpIfFalse [16]
   9: Ldar a0
  11: Sub [1], [1]
  13: Star a0
  15: JumpLoop [0], [15]
  17: ...

The structure is identical: condition → JumpIfFalse → body → JumpLoop. V8 adds feedback slots for profiling; you’ll add those when you implement optimization.

Implementation Steps

  1. Lexer: Add While to SymbolKind and recognize "while" as a keyword.
  2. AST: Add Stmt::While { condition, body } and Stmt::Assign { name, value }.
  3. Parser: Handle while in parse_stmt. Add lookahead in parse_expr_stmt to detect assignment.
  4. Bytecode: Add JumpLoop = 21 to the enum and the From<u8> / Display impls.
  5. Compiler: Compile While with the loop-start / JumpIfFalse / body / JumpLoop pattern. Compile Assign as expr + Star.
  6. VM: Add the JumpLoop handler (read byte, advance, subtract).
  7. Test: 
    let x = 10; let total = 0; while (x > 0) { total = total + x; x = x - 1; } total;
    → should produce 55.
Test incrementally. Get variable reassignment working first: let x = 10; x = 20; x; → 20. Then add while with a simple countdown: let x = 3; while (x > 0) { x = x - 1; } x; → 0. Then try the accumulator pattern.

Why does V8 use a separate JumpLoop opcode instead of allowing Jump to take negative offsets?
Negative offsets would require 16-bit operands
Back edges need runtime checks (stack overflow, GC, optimization) that forward jumps don’t
The VM can’t subtract from the program counter
V8 doesn’t support while loops in the interpreter

What This Unlocks

With while and variable reassignment, your VM can express:

  • Iterative algorithms: sum, factorial, GCD, any accumulator pattern
  • String building: while (i < 10) { s = s + "x"; i = i + 1; }
  • Bounded iteration: repeat N times without recursion or stack risk

Still missing (future lessons):

  • for loops: syntactic sugar — for (init; cond; update) desugars to init; while (cond) { body; update; }
  • break/continue: require tracking the loop’s exit and header addresses during compilation
  • Upvalue capture: closures that read/write variables from enclosing scopes
