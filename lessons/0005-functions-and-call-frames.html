Functions and Call Frames

Lesson 5 · g8 bytecode compiler · Prev: Variables · Reference: Instruction Set

Right now your VM has one instruction pointer, one register file, and runs one flat program. Functions break all three of those assumptions. A function call means: pause what you're doing, start executing different bytecode with fresh registers, then come back.

The structure that makes this work is a call frame.

What changes

Each function gets its own bytecode

When you compile function add(a, b) { return a + b; }, the body compiles to its own separate bytecode — its own code []byte, its own cons []int, and its own register numbering starting from 0. It's essentially a mini-Program.

The function's parameters are assigned to the first registers: a → r0, b → r1. The body compiles against those bindings. From the function's perspective, it's the same compilation you've already built — the only difference is that some registers are pre-populated with argument values instead of being empty.

The call stack

The VM no longer has a single ip and a single register file. Instead it has a stack of call frames. Each frame holds:

FieldWhat it is
bytecodePointer to the function's bytecode (code + constants)
ipInstruction pointer within this function's code
regsThis function's register file — parameters + locals + temporaries

The VM always executes from the top frame. When it reads an opcode, it reads from the top frame's bytecode at the top frame's ip. When it accesses a register, it's the top frame's register file.

Two new opcodes

OpcodeOperandsWhat it does
OpCall func_idx, arg_count Push a new call frame for the function. Copy argument values from the caller's registers into the callee's r0, r1, … Start executing the function's bytecode.
OpReturn none Pop the current call frame. The return value is in the accumulator — it survives the frame pop. The caller resumes execution with the result in acc.
V8 does this too. Each JavaScript function compiles to its own Ignition bytecode. CallUndefinedReceiver pushes a frame; Return pops it. Arguments are passed in consecutive registers. The accumulator holds the return value.

Source: V8's bytecodes.h

Worked example

Source:

function add(a, b) {
    return a + b;
}
let result = add(10, 20);

Step 1: Compile the function body

The function add gets its own bytecode. Parameters a and b are pre-assigned to r0 and r1: 

// add's bytecode (func index 0)
// symbols: {"a": 0, "b": 1}, nextReg starts at 2

Ldar   r0         // acc = a
Star   r2         // r2 = a (temp stash for +)
Ldar   r1         // acc = b
Add    r2         // acc = r2 + acc = a + b
Return            // return acc to caller

Step 2: Compile the main program

The FuncDecl doesn't emit any bytecode in the main program — it just registers the compiled function in a table. The call site compiles each argument, stashes them in consecutive registers, then emits OpCall: 

// main program bytecode
// funcs[0] = add's bytecode

// let result = add(10, 20);

// Compile arg 0:
LdaSmi [0]        // acc = 10
Star   r0         // r0 = 10 (arg 0)

// Compile arg 1:
LdaSmi [1]        // acc = 20
Star   r1         // r1 = 20 (arg 1)

// Call:
Call   0, 2       // call funcs[0] with 2 args from r0,r1
                  // → pushes new frame, copies r0→callee.r0, r1→callee.r1
                  // → executes add's bytecode
                  // → Return pops frame, acc = 30

// Store result:
Star   r2         // r2 = 30
                  // symbols["result"] = 2

Constants: [10, 20]

The argument passing convention

When compiling a call expression like add(10, 20), the compiler:

  1. Compiles each argument expression in order
  2. Stars each result into a consecutive register (r0, r1, …)
  3. Emits OpCall <func_idx> <arg_count>

The VM then copies those registers from the caller's frame into the callee's r0, r1, … — matching the parameter order. The callee's compiler already assigned a → r0, b → r1, so the values land in the right place.

Where do the argument registers come from? The simplest approach: the compiler records the first register used for arguments. Since allocReg() is sequential, if you allocate arg_count registers right before the call, they'll be consecutive. Pass the starting register as part of OpCall, or let the VM infer it from arg_count (the last N allocated registers).

Data structures

Here's what changes in your codebase:

A function bytecode type

type FuncBytecode struct {
    Code       []byte
    Cons       []int
    ParamCount int
}

This is the compiled form of a function. It's like a Program but without the symbol table (that's only needed during compilation). The main program holds a slice of these: 

type Program struct {
    code    []byte
    cons    []int
    funcs   []*FuncBytecode  // compiled functions
    nextReg int
    symbols map[string]int
}

Call frames in the VM

type CallFrame struct {
    bytecode *FuncBytecode
    ip       int
    regs     [256]int
}

type VM struct {
    acc    int
    frames []CallFrame  // call stack
}

The VM always operates on the top frame: frames[len(frames)-1]. The accumulator is shared across frames — it doesn't get saved/restored. This is how V8 does it: Return simply leaves the value in acc, and the caller picks it up from there.

The FDE loop

func (vm *VM) FDE() int {
    for len(vm.frames) > 0 {
        frame := &vm.frames[len(vm.frames)-1]

        if frame.ip >= len(frame.bytecode.Code) {
            // implicit return at end of function
            vm.frames = vm.frames[:len(vm.frames)-1]
            continue
        }

        op := ByteCode(frame.bytecode.Code[frame.ip])
        frame.ip++

        switch op {
        case OpLdaSmi:
            idx := frame.bytecode.Code[frame.ip]
            frame.ip++
            vm.acc = frame.bytecode.Cons[idx]

        case OpStar:
            r := frame.bytecode.Code[frame.ip]
            frame.ip++
            frame.regs[r] = vm.acc

        case OpLdar:
            r := frame.bytecode.Code[frame.ip]
            frame.ip++
            vm.acc = frame.regs[r]

        case OpAdd:
            r := frame.bytecode.Code[frame.ip]
            frame.ip++
            vm.acc = frame.regs[r] + vm.acc

        case OpMul:
            r := frame.bytecode.Code[frame.ip]
            frame.ip++
            vm.acc = frame.regs[r] * vm.acc

        case OpCall:
            funcIdx := frame.bytecode.Code[frame.ip]
            frame.ip++
            argCount := frame.bytecode.Code[frame.ip]
            frame.ip++

            fn := // ... look up the function bytecode
            newFrame := CallFrame{bytecode: fn}
            // Copy args: caller's last N registers → callee's r0..rN-1
            for i := 0; i < int(argCount); i++ {
                newFrame.regs[i] = frame.regs[/* arg register */]
            }
            vm.frames = append(vm.frames, newFrame)

        case OpReturn:
            // acc already holds the return value
            vm.frames = vm.frames[:len(vm.frames)-1]
        }
    }
    return vm.acc
}

How the compiler changes

Compiling FuncDecl

A function declaration doesn't emit bytecode in the main program. Instead it:

  1. Creates a fresh compilation context (new code, cons, symbols, nextReg)
  2. Pre-assigns each parameter to a register: symbols["a"] = 0, symbols["b"] = 1, nextReg = 2
  3. Compiles the function body's statements
  4. Wraps it in a FuncBytecode and appends to program.funcs
  5. Records the function's index so CallExpr can reference it: symbols["add"] = funcIndex (or use a separate funcTable map[string]int)

Compiling CallExpr

case *CallExpr:
    // Compile each argument, stash in consecutive registers
    firstReg := p.nextReg
    for _, arg := range expr.Args {
        p.CompileExpr(arg)
        reg := p.allocReg()
        p.code = append(p.code, byte(OpStar), byte(reg))
    }
    // Emit the call
    funcIdx := p.funcTable[expr.Func]
    p.code = append(p.code, byte(OpCall), byte(funcIdx), byte(len(expr.Args)))
    // After call: result is in accumulator

Compiling ReturnStmt

case *ReturnStmt:
    p.CompileExpr(stmt.Value)
    p.code = append(p.code, byte(OpReturn))

Now implement it

This is the biggest change yet. Take it in stages and test each one:

  1. Add the data structures: FuncBytecode, CallFrame, the funcs slice on Program. Add OpCall and OpReturn to your opcode enum and disassembler.
  2. Compile a simple function: Test that function add(a, b) { return a + b; } produces the right bytecode with a=r0, b=r1.
  3. Compile a call: Test that add(10, 20) emits argument loads, stars, and OpCall.
  4. Update the VM: Replace the single ip/regs with a frame stack. Add OpCall and OpReturn handlers.
  5. End-to-end test: function add(a, b) { return a + b; } let result = add(10, 20); → acc = 30.
Design decision: where do functions live? You need a way for OpCall in the main bytecode to find the function's FuncBytecode. Simplest approach: store them in a funcs []*FuncBytecode on the program, and OpCall's operand is an index into that slice. You also need a way for the VM to find the slice — either pass it to FDE or store it on the VM.

What's next

With functions, your language is Turing-complete (given recursion). Future directions:

  • Recursion — it already works if your call stack handles it, but test it with factorial or Fibonacci
  • Closures — functions that capture variables from their enclosing scope (requires context objects, like V8's LdaContextSlot)
  • V8 embedding — now that you have a complete mental model of how bytecode VMs work, you can start looking at v8go and real V8 isolates
