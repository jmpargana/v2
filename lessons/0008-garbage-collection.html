Garbage Collection

Lesson 8 · ~30 min · Prerequisite: Lesson 7

Your heap has a problem: it only grows. Every alloc_string appends bytes, and nothing ever reclaims them. Run a loop that allocates strings, and your Vec<u8> grows without bound.

This lesson introduces garbage collection — the mechanism that identifies dead heap objects and reclaims their memory. You’ll implement a mark-compact collector: find what’s alive, copy it to a fresh heap, and throw the rest away.

What’s Alive?

An object is alive if any running code can still reach it. The starting points for reachability are called roots — the values the VM is actively using:

  • The accumulator (vm.acc)
  • Every register in every active call frame (frame.reg[0..256])
  • Every constant in every loaded program (program.cons)

If a root holds a tagged Value with bit 0 = 1, the heap object at that offset is alive. Everything else is garbage.

Simplification: Your heap objects (strings) don’t reference other heap objects. That means reachability is flat — just check the roots directly, no recursive traversal needed. When you later add objects with properties (which hold Values that might themselves be heap pointers), you’ll need to walk the object graph recursively. For now, roots are enough.

The Algorithm: Mark and Compact

Three phases:

Phase 1 — Mark

Scan every root. Collect the heap offsets of all live objects into a set.

roots:  [Smi(10), HeapObj(@0), Smi(5), HeapObj(@15), HeapObj(@0)]
                       │                     │              │
live offsets:        { 0, 15 }       (duplicates ignored)

Phase 2 — Compact

Walk the heap from offset 0 to the end. For each object, check if it’s in the live set. If yes, copy it to a new Vec<u8> and record where it moved. If no, skip it. 

Old heap:
  @0:  [String "hello"]  (10 bytes) — LIVE
  @10: [String "temp"]   (9 bytes)  — DEAD
  @19: [String "world"]  (10 bytes) — LIVE

New heap (compacted):
  @0:  [String "hello"]  (10 bytes)
  @10: [String "world"]  (10 bytes)

Remap:  { 0 → 0,  19 → 10 }

The dead string "temp" at offset 10 is gone. "world" moved from offset 19 to offset 10. The heap shrank from 29 bytes to 20.

Phase 3 — Update pointers

Every root that held a heap pointer needs its offset updated according to the remap. A register that held Value::from_heap(19) now holds Value::from_heap(10).

Walking the Heap

To compact, you need to iterate through objects in the heap. But the heap is a raw Vec<u8> — how do you know where one object ends and the next begins?

Each object is self-describing: the type byte tells you the object’s kind, and from that you can compute its total size in bytes. For strings: 

object_size(offset):
  type_byte = heap[offset]       // 1 = String
  match type_byte:
    String:
      len = u32 from heap[offset+1 .. offset+5]
      total = 1 + 4 + len         // type + length + data

With object_size, you can walk the entire heap: start at offset 0, compute size, jump forward, repeat until you reach the end. This is how GCs iterate through all objects — the heap is a flat array of self-describing objects.

A String object holding "foo" starts at heap offset 20. What is the offset of the next object after it?
Offset 23 (20 + 3 bytes of data)
Offset 27 (20 + 4 length + 3 data)
Offset 28 (20 + 1 type + 4 length + 3 data)
Offset 24 (20 + 4 length)

Why Compact Instead of Free-in-Place?

You could mark dead objects and add them to a free list — track the gaps and reuse them later. That’s what mark-sweep does. But it has a problem: fragmentation. After many allocations and sweeps, the heap becomes a patchwork of small free regions that can’t hold large objects even though the total free space is enough.

Mark-compact avoids this by rebuilding the heap with all live objects packed together. Allocation stays simple: always append to the end. The tradeoff is that every collection copies all live objects and updates all pointers, which is O(live data). For V8’s young generation (Scavenger), this is fine — most young objects die quickly, so there’s very little to copy.

Implementation

Step 1: Heap::object_size

Add a method that calculates the total byte size of the object at a given offset:

fn object_size(&self, offset: usize) -> usize {
    match self.bytes[offset] {
        1 => { // InstanceType::String
            let len_bytes: [u8; 4] = self.bytes[offset+1..offset+5]
                .try_into().unwrap();
            let len = u32::from_le_bytes(len_bytes) as usize;
            1 + 4 + len
        }
        t => panic!("unknown object type {} at offset {}", t, offset),
    }
}

Test: allocate a string, verify object_size(0) returns the right value.

Step 2: Heap::collect

Takes a set of live heap offsets (from the mark phase), compacts the heap, and returns the offset remap so the caller can update its pointers: 

use std::collections::{HashMap, HashSet};

pub fn collect(
    &mut self,
    live: &HashSet<usize>,
) -> HashMap<usize, usize> {
    let mut new_bytes = Vec::new();
    let mut remap = HashMap::new();
    let mut pos = 0;

    while pos < self.bytes.len() {
        let size = self.object_size(pos);
        if live.contains(&pos) {
            let new_offset = new_bytes.len();
            remap.insert(pos, new_offset);
            new_bytes.extend_from_slice(
                &self.bytes[pos..pos + size]
            );
        }
        pos += size;
    }

    self.bytes = new_bytes;
    remap
}

The caller (the VM) is responsible for two things:

  1. Building the live set by scanning its roots
  2. Applying the remap to every Value it holds

Step 3: VM integration

Add a collect_garbage method to the VM that orchestrates the three phases. The tricky part is gathering all roots — the accumulator, every register in every active frame, and every constant in the program tree: 

fn collect_garbage(
    &mut self,
    stack: &mut Vec<Frame>,
    program: &mut Program,
) {
    // Phase 1: Mark — find all live heap offsets
    let mut live = HashSet::new();
    if self.acc.is_heap_object() {
        live.insert(self.acc.heap_offset());
    }
    for frame in stack.iter() {
        for val in frame.reg.iter() {
            if val.is_heap_object() {
                live.insert(val.heap_offset());
            }
        }
    }
    // Also scan constant pools (they hold heap pointers to string literals)
    Self::scan_program_cons(program, &mut live);

    // Phase 2: Compact
    let remap = self.heap.collect(&live);

    // Phase 3: Update pointers
    Self::remap_value(&mut self.acc, &remap);
    for frame in stack.iter_mut() {
        for val in frame.reg.iter_mut() {
            Self::remap_value(val, &remap);
        }
    }
    Self::remap_program_cons(program, &remap);
}

fn remap_value(val: &mut Value, remap: &HashMap<usize, usize>) {
    if val.is_heap_object() {
        if let Some(&new_offset) = remap.get(&val.heap_offset()) {
            *val = Value::from_heap(new_offset);
        }
    }
}

You’ll also need helper methods to scan and remap constant pools across the program tree (the main program and all its nested function programs).

Step 4: Triggering collection

When should the GC run? Two common strategies:

  • Allocation threshold: collect when heap.bytes.len() exceeds some limit (e.g., 1024 bytes). After collection, double the threshold if the heap is still >50% full.
  • Allocation count: collect every N allocations. Simpler but less adaptive.

Start with a byte threshold. Add a threshold field to Heap, check it in alloc_string, and call back into the VM’s collect method when exceeded.

Rust ownership note: The GC needs mutable access to the heap, the frame stack, and the program simultaneously. Your current fde method borrows &Program immutably. To update constant pools during GC, you’ll either need to make that borrow mutable, or separate the constant pool from the Program struct. This is a real design tension — V8 solves it by having a dedicated GC phase where the mutator (running code) is paused and the entire heap + roots are accessible. In Rust, you’re forced to make this explicit. It’s a good first taste of the constraints that shape real GC implementations.

  • Empty live set: collect with no roots — heap should be empty after

How V8 Does It

V8 uses a generational garbage collector based on the observation that most objects die young (the generational hypothesis):

  • Young generation (Scavenger): A semi-space copying collector. Two equal halves — allocate in one, copy survivors to the other, swap. Very fast because most young objects are garbage. This is closest to what you’re building.
  • Old generation (Major GC): Mark-sweep-compact. Objects that survive multiple young-gen collections get promoted here. Collected less frequently.

Your mark-compact collector is a simplified version of both — it copies survivors (like the Scavenger) and compacts (like the major GC). As your VM grows, you could split the heap into two generations. For now, one collector is enough.
