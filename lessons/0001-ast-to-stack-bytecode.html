From AST to Stack-Based Bytecode

Lesson 1 · g8 bytecode compiler · Reference: Instruction Set

You have an AST. It's a tree of nodes — binary operations with children, leaf integers at the tips. A tree is great for representing structure, but a machine doesn't execute trees. It executes a flat sequence of instructions, one after another. Bytecode is that flat sequence.

The question is: how do you flatten a tree into a list, and still get the right answer?

The idea: a stack machine

The simplest execution model is a stack machine. It has one data structure: a stack. Every instruction does one of two things:

  1. Push a value onto the stack
  2. Pop operands, compute, push the result

For your grammar (integers, +, *), you need exactly three instructions:

InstructionWhat it does
OpPush <idx>Push constants[idx] onto the stack
OpAddPop two values, push their sum
OpMulPop two values, push their product

That's the entire instruction set. Three opcodes are enough to evaluate any expression your parser can produce.

Why a stack? A stack machine is where almost every bytecode VM starts — the JVM, CPython, WebAssembly, Lua 4. V8's Ignition uses a register machine instead (we'll get there). But the stack model is the right first step: it's simpler, and the compilation algorithm is almost trivial.

Source: Crafting Interpreters, Ch. 14

The algorithm: post-order traversal

Here's the key insight. Look at this AST for 30 + (20 * 40): 

       ADD
      /   \
    30    MUL
         /   \
       20    40

A stack machine needs operands on the stack before the operator runs. So you compile children first, parent last. That's a post-order traversal: 

compile(node):
  if node is a leaf:
    emit OpPush with the value
  else:
    compile(node.Left)   // left operand first
    compile(node.Right)  // right operand second
    emit the operator    // operator last

Applied to the tree above: 

compile(ADD)
  compile(30)        → OpPush 0      // constants[0] = 30
  compile(MUL)
    compile(20)      → OpPush 1      // constants[1] = 20
    compile(40)      → OpPush 2      // constants[2] = 40
    emit MUL         → OpMul
  emit ADD           → OpAdd

Final bytecode:

OpPush 0    // push 30
OpPush 1    // push 20
OpPush 2    // push 40
OpMul       // pop 20, 40 → push 800
OpAdd       // pop 30, 800 → push 830

Why this works

The post-order traversal preserves evaluation order. Each subtree compiles to a sequence of instructions that, when executed, leaves exactly one value on the stack — the subtree's result. The parent's operator instruction then consumes those results.

This is the stack discipline: every well-formed subtree has a net stack effect of +1. Leaves push one value (+1). Binary operators push two subtrees (+2) and then pop two and push one (−2 + 1 = −1), for a net of +1.

This is the same idea as Reverse Polish Notation. The bytecode 30 20 40 * + is literally RPN. If you've ever used an HP calculator, you already know how a stack machine works.

The constant pool

Notice that literal values don't appear in the bytecode itself. Instead, they go into a separate constant pool — an array of values. The OpPush instruction carries an index into this pool, not the value itself.

Why the indirection? Because bytecode instructions should be fixed-width (or at least small). An integer might be 8 bytes, but a pool index is 1 byte. This keeps the instruction stream compact and cache-friendly.

One-byte indices limit you to 256 constants per program. That's fine for now. When it isn't, you add an OpPushWide with a 2-byte operand — same idea, more room.

Now implement it

You have everything you need. Open bytecode.go and build the compiler. Here's the skeleton — the structure maps directly to the algorithm above: 

type OpCode byte

const (
    OpPush OpCode = iota
    OpAdd
    OpMul
)

type Program struct {
    Code      []byte
    Constants []int
}

func Compile(node *AST) *Program {
    p := &Program{}
    p.compile(node)
    return p
}

func (p *Program) compile(node *AST) {
    if node.Value != nil {
        // Leaf: add the value to the constant pool,
        // emit OpPush with the pool index
        idx := len(p.Constants)
        p.Constants = append(p.Constants, *node.Value)
        p.Code = append(p.Code, byte(OpPush), byte(idx))
        return
    }

    // Binary op: compile children first (post-order)
    p.compile(node.Left)
    p.compile(node.Right)

    // Then emit the operator
    switch node.Op {
    case OADD:
        p.Code = append(p.Code, byte(OpAdd))
    case OMUL:
        p.Code = append(p.Code, byte(OpMul))
    }
}

Then write a test: lex 30 + (20 * 40), parse it, compile it, and check that Program.Code is [OpPush, 0, OpPush, 1, OpPush, 2, OpMul, OpAdd] and Program.Constants is [30, 20, 40].

Don't skip the test. The compiler is simple now, but it won't stay simple. A test for the compilation output is the single most useful thing you can write — it will catch regressions every time you add a new node type.

What's next

You can compile an AST to bytecode. But bytecode sitting in memory doesn't do anything — you need a virtual machine to execute it. Next lesson: build a stack-based VM that reads your bytecode and produces a result.

After that, we'll look at how V8's Ignition does it differently (registers instead of a stack, an accumulator, bytecode handlers) and start thinking about what it takes to target a real V8 isolate.
