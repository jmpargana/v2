For Loops — Syntactic Sugar

Lesson 12 · ~20 min · Prev: Lesson 11 · Reference: Instruction Set

A for loop is not a new concept for the VM. It’s syntactic sugar — a nicer way to write something the compiler already knows how to do. This lesson adds zero new bytecodes. The parser does all the work: it reads for syntax and produces AST nodes that the compiler already handles.

The Desugaring

Every for loop maps directly onto a while loop: 

// Source:
for (let i = 0; i < 10; i = i + 1) {
    total = total + i;
}

// Desugars to:
let i = 0;
while (i < 10) {
    total = total + i;
    i = i + 1;
}

The three parts of the for header — init, condition, update — just rearrange into a while loop:

  1. Init runs once, before the loop.
  2. Condition becomes the while condition.
  3. Update appends to the end of the body.
for (init; condition; update) { body }
    ↓
init;
while (condition) { body; update; }
How many new bytecodes does adding for loops require?
1 — a ForLoop opcode
2 — ForInit and ForUpdate
0 — it desugars to existing while-loop bytecodes
3 — ForInit, ForCondition, ForUpdate

Two Approaches to Desugaring

There are two ways to implement this, and both are legitimate:

Option A: Desugar in the parser

The parser reads for syntax and emits existing AST nodes. No Stmt::ForLoop variant needed. The compiler never knows a for loop existed: 

fn parse_for_loop(&mut self) -> Vec<Stmt> {
    // Returns multiple statements: [init, while_loop]
    ...
}

Option B: Add a ForLoop AST node

The parser creates a Stmt::ForLoop, and the compiler desugars it during compilation by compiling the init, then entering a while-style loop: 

Stmt::ForLoop { init, condition, update, body }

Option A is simpler (fewer changes). Option B preserves source structure in the AST, which matters if you ever want to pretty-print or debug the AST. Both produce identical bytecode.

V8’s approach: V8 uses Option B. The AST has a ForStatement node, and the bytecode generator handles it explicitly in VisitForStatement. But the bytecodes it emits are the same as a while — condition, JumpIfFalse, body, update, JumpLoop. The AST distinction matters for V8 because it feeds into scope analysis, debugging, and source mapping. For a teaching VM, either approach works.

Lexer: the for keyword

Add For to SymbolKind and recognize it in the keyword match: 

// lex.rs
pub enum SymbolKind {
    // ... existing variants ...
    For,
}

// In the keyword match:
"for" => res.push(Symbol {
    kind: SymbolKind::For,
    int_val: None,
    str_val: String::new(),
}),

AST: the ForLoop node

We’ll use Option B — an explicit AST node. This keeps the parser clean and preserves the source structure: 

pub enum Stmt {
    // ... existing variants ...
    ForLoop {
        init: Box<Stmt>,
        condition: Expr,
        update: Box<Stmt>,
        body: Vec<Stmt>,
    },
}

init is typically a VarDecl. update is typically an Assign. Both are Box<Stmt> because the enum is recursive.

Parser

Add SymbolKind::For to the parse_stmt dispatch, then parse the three-part header: 

fn parse_stmt(&mut self) -> Stmt {
    match self.peek() {
        // ... existing arms ...
        SymbolKind::For => self.parse_for_loop(),
        _ => self.parse_expr_stmt(),
    }
}

fn parse_for_loop(&mut self) -> Stmt {
    self.expect(SymbolKind::For);
    self.expect(SymbolKind::LPar);

    // Init: typically "let i = 0;"
    let init = self.parse_stmt();

    // Condition: typically "i < 10"
    let condition = self.parse_expr();
    self.expect(SymbolKind::Semi);

    // Update: typically "i = i + 1" (no trailing semicolon — RPar follows)
    let update = self.parse_for_update();
    self.expect(SymbolKind::RPar);

    // Body
    self.expect(SymbolKind::LBrace);
    let mut body = Vec::new();
    while self.peek() != SymbolKind::RBrace {
        body.push(self.parse_stmt());
    }
    self.expect(SymbolKind::RBrace);

    Stmt::ForLoop {
        init: Box::new(init),
        condition,
        update: Box::new(update),
        body,
    }
}

Parsing the update clause

The update clause is tricky. i = i + 1 looks like an assignment statement, but it doesn’t end with ; — it’s followed by ). You need a separate parser for this: 

fn parse_for_update(&mut self) -> Stmt {
    if self.peek() == SymbolKind::Ident
        && self.pos + 1 < self.syms.len()
        && self.syms[self.pos + 1].kind == SymbolKind::Assign
    {
        let name = self.pop().str_val;
        self.expect(SymbolKind::Assign);
        let value = self.parse_expr();
        return Stmt::Assign { name, value };
    }
    let expr = self.parse_expr();
    Stmt::ExprStmt(expr)
}

This is identical to parse_expr_stmt but without the trailing expect(Semi).

Why does the update clause need its own parsing function instead of reusing parse_expr_stmt?
The update might be an expression, not a statement
The update is not followed by a semicolon — ) comes next
The update runs in a different scope
The update can contain multiple statements

Compiler: Desugaring at Compile Time

The compiler treats ForLoop exactly like its while equivalent. This is the elegant payoff — all the hard work was done in Lesson 11: 

Stmt::ForLoop { init, condition, update, body } => {
    // 1. Compile the initializer (runs once)
    self.compile_stmt(init, heap);

    // 2. Record loop start (same as while)
    let loop_start = self.code.len();

    // 3. Compile condition + exit jump (same as while)
    self.compile_expr(condition, heap);
    let exit_jump = self.emit_jump(ByteCode::JumpIfFalse);

    // 4. Compile body (same as while)
    self.compile_stmts(body, heap);

    // 5. Compile the update (runs after each iteration)
    self.compile_stmt(update, heap);

    // 6. JumpLoop back to condition (same as while)
    self.code.push(ByteCode::JumpLoop as u8);
    self.code.push((self.code.len() + 1 - loop_start) as u8);

    // 7. Patch exit jump (same as while)
    self.patch_jump(exit_jump);
}

Steps 2, 3, 6, and 7 are identical to WhileLoop compilation. Steps 1 and 5 are the only additions — compiling init before the loop and update at the end of each iteration. The bytecodes emitted are the same ones you’ve been using all along.

Compare this with the while version of the same program: the bytecode is identical. The for syntax just let the programmer put the init, condition, and update on one line instead of three.

Why Syntactic Sugar Matters

“Syntactic sugar” sounds dismissive, but it’s one of the most important concepts in language design. Here’s why:

  1. Zero runtime cost. The bytecodes are identical. There’s no “for loop overhead” — the VM literally cannot tell whether the source was for or while.
  2. Locality of intent. for (let i = 0; i < n; i = i + 1) puts the loop variable, its bound, and its increment in one place. With while, these are scattered across three locations, inviting bugs (forget the increment? infinite loop).
  3. Compiler simplicity. No new bytecodes, no new VM handlers, no new optimization paths. The compiler reuses everything from while.
Real-world example: Python’s for x in range(n), JavaScript’s for...of, and Rust’s for x in 0..n all desugar to iterator-based loops internally. The surface syntax is different; the underlying mechanism is shared. This is the same principle at a larger scale.

How V8 Compiles For Loops

V8’s bytecode generator handles for in VisitForStatement:

// Pseudocode of V8's VisitForStatement
void BytecodeGenerator::VisitForStatement(ForStatement* stmt) {
    // 1. Compile init
    Visit(stmt->init());

    // 2. Loop header
    LoopBuilder loop_builder(this);
    loop_builder.LoopHeader();

    // 3. Condition + exit
    if (stmt->cond()) {
        Visit(stmt->cond());
        loop_builder.BreakIfFalse();
    }

    // 4. Body
    Visit(stmt->body());

    // 5. Update + back edge
    Visit(stmt->next());
    loop_builder.JumpToHeader();
}

The structure is the same: init → loop header → condition → JumpIfFalse → body → update → JumpLoop. V8’s LoopBuilder handles the offset bookkeeping that you do manually with emit_jump and patch_jump.

In the compiled bytecode for for (init; cond; update) { body }, where does the update code appear?
After the body, before JumpLoop
Before the condition, after JumpLoop
At the beginning of the body
After JumpLoop, before the exit point

Implementation Steps

  1. Lexer: Add For to SymbolKind and recognize "for" as a keyword.
  2. AST: Add Stmt::ForLoop { init, condition, update, body }. Add Display for the new variant.
  3. Parser: Handle SymbolKind::For in parse_stmt. Write parse_for_loop and parse_for_update (like parse_expr_stmt but without trailing semicolon).
  4. Compiler: Match Stmt::ForLoop — compile init, then the standard while-loop pattern with update before JumpLoop.
  5. Test: 
    var total = 0; for (var i = 1; i <= 5; i = i + 1) { total = total + i; } total;
    → should produce 15.
The update clause is the only tricky part. Everything else reuses existing infrastructure. If your while-loop tests pass, for loop compilation will work on the first try — the bytecode patterns are identical.

What This Unlocks

With for loops, your VM can express:

  • Counted iteration: for (let i = 0; i < n; i = i + 1)
  • Summation: for (let i = 1; i <= n; i = i + 1) { total = total + i; }
  • Nested loops: for (...) { for (...) { ... } }

Still missing (future lessons):

  • break/continue: require tracking the loop’s exit and header addresses during compilation, and a loop-context stack in the compiler
  • do-while: like while but the condition check is at the bottom — the body always executes at least once
  • for...in/for...of: require iterators and object/array support
