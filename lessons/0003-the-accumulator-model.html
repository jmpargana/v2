The Accumulator Model

Lesson 3 · g8 bytecode compiler · Prev: Building the VM · Reference: Instruction Set

Your stack machine works. But V8 doesn't use a stack machine. It uses a register machine with an accumulator. This lesson explains why, what that means, and how to convert your compiler and VM to use it.

The problem with stacks

Look at your bytecode for 30 + (20 * 40): 

OpPush 0    // push 30
OpPush 1    // push 20
OpPush 2    // push 40
OpMul       // pop 20, pop 40, push 800
OpAdd       // pop 30, pop 800, push 830

Every value passes through the stack. The value 30 is pushed, then sits there doing nothing while the multiplication happens, then gets popped for the addition. That's three memory operations (push, idle, pop) for a value that just needs to wait.

In a more complex expression, this gets worse. Values get pushed and popped repeatedly as they flow through nested subexpressions. Each push/pop is a memory access — and memory is slow compared to registers.

The bigger issue: a stack is opaque to the optimizer. If you wanted to optimize the bytecode later (reorder instructions, eliminate redundant operations), everything is implicit — you can't look at an instruction and know which value it operates on without simulating the entire stack up to that point.

The register idea

A register machine names its temporaries. Instead of pushing onto an anonymous stack, you say which register holds each value: 

Load  r0, 30      // r0 = 30
Load  r1, 20      // r1 = 20
Load  r2, 40      // r2 = 40
Mul   r1, r1, r2  // r1 = r1 * r2 = 800
Add   r0, r0, r1  // r0 = r0 + r1 = 830

Now every instruction says exactly what it reads and writes. No implicit state. An optimizer can see that r0 isn't touched by the Mul, so it could freely reorder things.

The tradeoff: instructions are bigger (three register operands per binary op), and the compiler needs a register allocator — it has to decide which register holds which value.

V8's compromise: the accumulator

V8's Ignition interpreter doesn't go full three-address register machine. Instead it uses a hybrid: one special register (the accumulator) is implicit in most instructions. Binary operations read one operand from a named register and the other from the accumulator, and write the result back to the accumulator.

This means most instructions only need to encode one register operand instead of three — keeping bytecode compact — while still giving you named storage for values that need to wait.

Here are the key V8 bytecodes (simplified for your grammar):

BytecodeOperationDescription
LdaSmi <imm> acc = imm Load a small integer into the accumulator
Star <reg> reg = acc Store the accumulator into a register
Ldar <reg> acc = reg Load a register into the accumulator
Add <reg> acc = reg + acc Add register to accumulator
Mul <reg> acc = reg * acc Multiply register by accumulator
Where's OpPush? Gone. There is no stack to push onto. Values live in the accumulator or in named registers. The accumulator replaces the top-of-stack as the "current working value."

Source: V8's bytecodes.h and the Ignition blog post

Your expression, accumulator-style

Let's compile 30 + (20 * 40) to accumulator bytecode. The trick: when you need a value to survive past the next operation, stash it in a register with Star. Otherwise, let it ride in the accumulator. 

LdaSmi 30     // acc = 30
Star   r0     // r0 = 30  (stash — we need 30 later)
LdaSmi 20     // acc = 20
Star   r1     // r1 = 20  (stash — Mul needs it in a register)
LdaSmi 40     // acc = 40
Mul    r1     // acc = r1 * acc = 20 * 40 = 800
Add    r0     // acc = r0 + acc = 30 + 800 = 830

Compare to the stack version (5 instructions, stack depth 3):

OpPush 0, OpPush 1, OpPush 2, OpMul, OpAdd

The accumulator version is 7 instructions. More instructions, but each one is explicit about what it reads and writes. And there's no stack at all — just the accumulator and two registers.

The compilation algorithm

The compiler still walks the AST in post-order. But now it needs a register counter — a simple allocator that hands out the next free register each time a value needs to be stashed.

The rule for each node type:

  • Leaf (integer literal): emit LdaSmi <value>. The value is now in the accumulator.
  • Binary op:
    1. Compile the left child (result lands in accumulator)
    2. Emit Star rN to stash the left result in a register
    3. Compile the right child (result lands in accumulator)
    4. Emit Add rN or Mul rN (operator uses the stashed left value)
func (p *RegProgram) compile(node *AST) {
    if node.Value != nil {
        p.emit(OpLdaSmi, byte(*node.Value))
        return
    }

    // Compile left → result in accumulator
    p.compile(node.Left)

    // Stash left result in a register
    reg := p.allocReg()
    p.emit(OpStar, reg)

    // Compile right → result in accumulator
    p.compile(node.Right)

    // Binary op: reg ○ acc → acc
    switch node.Op {
    case OADD:
        p.emit(OpRegAdd, reg)
    case OMUL:
        p.emit(OpRegMul, reg)
    }
}
This allocator leaks registers. It hands them out but never reclaims them. For your arithmetic expressions that's fine — the tree is small. A real compiler would track register lifetimes and reuse freed registers. V8 does this; you don't need to yet.

The new VM

The VM is almost the same loop, but instead of a stack it has an accumulator variable and a register array: 

type RegVM struct {
    ip   int
    acc  int
    regs [256]int
}

func (vm *RegVM) FDE(program RegProgram) int {
    for vm.ip < len(program.Code) {
        op := OpCode(program.Code[vm.ip])
        vm.ip++

        switch op {
        case OpLdaSmi:
            vm.acc = int(program.Code[vm.ip])
            vm.ip++
        case OpStar:
            r := program.Code[vm.ip]
            vm.ip++
            vm.regs[r] = vm.acc
        case OpLdar:
            r := program.Code[vm.ip]
            vm.ip++
            vm.acc = vm.regs[r]
        case OpRegAdd:
            r := program.Code[vm.ip]
            vm.ip++
            vm.acc = vm.regs[r] + vm.acc
        case OpRegMul:
            r := program.Code[vm.ip]
            vm.ip++
            vm.acc = vm.regs[r] * vm.acc
        }
    }
    return vm.acc
}

Notice: no Push, no Pop, no stack. The result is always in the accumulator when the program finishes.

Now implement it

You can build this alongside your existing stack machine — use different type names (RegProgram, RegVM) or put it in a separate file. The end-to-end test is the same: lex, parse, compile, run, assert 830.

One thing to decide: LdaSmi in V8 embeds the integer directly in the bytecode (no constant pool). For small integers that fit in a byte (0–255), this is simpler. For larger values, you could keep a constant pool and use a LdaConstant instruction instead. Start with the inline approach — it matches V8's design and eliminates the constant pool entirely for your current grammar.

What's next

With a register-based VM, you're now on the same architectural foundation as V8's Ignition. The next steps toward a V8 isolate:

  • Variables and let-bindings — registers become the natural home for local variables, which is exactly what V8 does
  • A disassembler — printing register-based bytecode is more useful than stack-based, since you can see the data flow
  • V8 embedding — using v8go or similar Go bindings to run code inside an actual V8 isolate
