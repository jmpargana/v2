Closures — Functions on the Heap

Lesson 10 · ~35 min · Prerequisite: Lesson 9

Your constant pool lives inside Program — a Rust struct outside the heap. The GC can’t trace it, can’t update it, and cloning it into frames creates stale pointers after compaction. The architecture described in the V8 object graph solves this by making functions heap objects. The constant pool lives inside the function on the heap, so the GC manages it like everything else.

This lesson restructures the heap to hold complex objects, introduces BytecodeFunction and Closure as heap types, and changes GC from flat root scanning to recursive graph tracing.

The Object Graph

Here’s what your runtime looks like after this lesson:

Isolate
├── acc: Value
├── heap: Heap
│   └── objects: Vec<Option<HeapObject>>
│       ├── [0] String("hello")
│       ├── [1] BytecodeFunction { code, cons: [Smi(10), @0], param_count, reg_count }
│       ├── [2] Closure { function: @1, upvalues: [] }
│       ├── [3] None  ← freed by GC, reusable
│       └── [4] String("world")
└── call_stack: Vec<Frame>
    └── Frame
        ├── ip: 6
        ├── reg: [Value; 256]
        └── closure: Value(@2)  ← heap pointer to Closure

A Frame doesn’t borrow a &Program anymore. It holds a Value that points to a Closure on the heap. The Closure points to a BytecodeFunction, also on the heap. The function’s constant pool contains Values that may point to other heap objects. The GC traces through all of this in one recursive pass.

Restructuring the Heap

Your current heap is a Vec<u8> with manual byte packing. That worked for strings, but packing bytecode arrays, constant pools, and cross-references into raw bytes gets painful. Time to upgrade: 

pub struct HeapString {
    pub data: String,
}

pub struct BytecodeFunction {
    pub code: Vec<u8>,
    pub cons: Vec<Value>,
    pub param_count: usize,
    pub reg_count: usize,
}

pub struct HeapClosure {
    pub function: Value,       // heap pointer to BytecodeFunction
    pub upvalues: Vec<Value>,  // captured variables
}

pub enum HeapObject {
    String(HeapString),
    Function(BytecodeFunction),
    Closure(HeapClosure),
}

pub struct Heap {
    objects: Vec<Option<HeapObject>>,
}

A heap pointer in a Value is now an index into objects instead of a byte offset. The tagging is the same — Value::from_heap(idx) still sets bit 0 to 1.

Why move away from Vec<u8>? Byte packing taught you how real heaps work at the metal. But for learning closures and GC tracing, the byte-packing complexity would dominate the lesson. V8 itself doesn’t use raw Vec<u8> — it has typed object layouts with header words and known field offsets. The enum approach captures the same structure more cleanly in Rust.

Allocation and Reading

impl Heap {
    pub fn alloc(&mut self, obj: HeapObject) -> Value {
        // Reuse a freed slot if available
        if let Some(idx) = self.objects.iter()
            .position(|o| o.is_none())
        {
            self.objects[idx] = Some(obj);
            return Value::from_heap(idx);
        }
        // Otherwise append
        let idx = self.objects.len();
        self.objects.push(Some(obj));
        Value::from_heap(idx)
    }

    pub fn read_string(&self, val: Value) -> &str {
        match &self.objects[val.heap_offset()] {
            Some(HeapObject::String(s)) => &s.data,
            other => panic!("expected String, got {:?}", other),
        }
    }

    pub fn read_function(&self, val: Value) -> &BytecodeFunction {
        match &self.objects[val.heap_offset()] {
            Some(HeapObject::Function(f)) => f,
            other => panic!("expected Function, got {:?}", other),
        }
    }

    pub fn read_closure(&self, val: Value) -> &HeapClosure {
        match &self.objects[val.heap_offset()] {
            Some(HeapObject::Closure(c)) => c,
            other => panic!("expected Closure, got {:?}", other),
        }
    }
}

alloc_string becomes heap.alloc(HeapObject::String(...)). Same for functions and closures. One allocation path for everything.

GC: Recursive Tracing

This is the big change. Your current GC scans roots and that’s it — strings don’t reference other objects. But now:

  • A Closure references a BytecodeFunction + upvalues
  • A BytecodeFunction’s constant pool contains Values that may point to strings, other functions, or other closures

The GC must trace the graph: visit a root, mark it, then recursively visit everything it references. 

impl Heap {
    pub fn collect(&mut self, roots: &[Value]) {
        // Mark phase: trace from roots
        let mut marked = vec![false; self.objects.len()];
        for &root in roots {
            self.mark(&mut marked, root);
        }
        // Sweep phase: free unmarked objects
        for i in 0..self.objects.len() {
            if !marked[i] {
                self.objects[i] = None;
            }
        }
    }

    fn mark(&self, marked: &mut Vec<bool>, val: Value) {
        if !val.is_heap_object() { return; }
        let idx = val.heap_offset();
        if idx >= self.objects.len() || marked[idx] { return; }
        marked[idx] = true;

        match &self.objects[idx] {
            Some(HeapObject::String(_)) => {
                // no references to trace
            }
            Some(HeapObject::Function(f)) => {
                for &v in &f.cons {
                    self.mark(marked, v);
                }
            }
            Some(HeapObject::Closure(c)) => {
                self.mark(marked, c.function);
                for &v in &c.upvalues {
                    self.mark(marked, v);
                }
            }
            None => {}
        }
    }
}
Key insight: mark takes &self (immutable) and &mut marked (a local Vec<bool>). Since marked is not part of self, Rust allows this — no borrow conflict. The sweep phase runs after marking is done, using &mut self.

No more remapping

Objects don’t move. A None slot is just a hole that gets reused on the next allocation. This means no remap, no pointer updating — heap indices stay stable across GC cycles. The entire stale-cons problem dissolves: the constant pool lives on the heap at a fixed index, and the GC keeps it alive by tracing through the closure.

The tradeoff: fragmentation. Many None holes waste space. V8 handles this with compaction in its old generation — you could add that later. For now, mark-sweep with slot reuse is clean and correct.

A Frame holds a Closure. The Closure points to a BytecodeFunction. The function’s constant pool holds a string. How does the GC know the string is alive?
The string is always alive because it’s a constant
The GC traces Closure → Function → cons → string
The VM registers the string as a separate root
Constants are stored outside the heap and never collected

Closures

A Closure is the runtime representation of a function. It has two parts:

  1. function: a heap pointer to the BytecodeFunction (the compiled template — code + constants). Multiple closures can share the same function.
  2. upvalues: the captured variables from enclosing scopes. This is what makes closures close over their environment.
// Shared template — one per function declaration
BytecodeFunction { code: [...], cons: [Smi(1), @3], param_count: 1, reg_count: 2 }

// Runtime instances — one per function() call site
Closure { function: @5, upvalues: [@7] }    // captures variable from outer scope
Closure { function: @5, upvalues: [@12] }   // same function, different capture

For now, if you don’t need variable capture yet, upvalues is an empty Vec. The Closure is still useful because it gives the GC a single root to trace for the entire function + its constants.

Upvalues: Capturing Variables

When a nested function references a variable from its enclosing function, that variable must outlive the enclosing function’s frame. Consider: 

function makeCounter() {
    let count = 0;
    function increment() {
        count = count + 1;
        return count;
    }
    return increment;
}
let counter = makeCounter();
counter();  // 1
counter();  // 2

After makeCounter returns, its frame is gone — but count must survive because increment still uses it. An upvalue is the mechanism that makes this work:

Open upvalue

While the enclosing function is still running, the upvalue points to the variable’s slot on the call stack. Reads and writes go straight to the live register: 

Upvalue::Open { frame_idx: 0, reg: 3 }
  // reads/writes frame 0, register 3 directly

Closed upvalue

When the enclosing frame pops, the variable would be destroyed. Instead, its value is copied into the upvalue itself. The upvalue now owns the value: 

// Before frame pop:  Upvalue::Open { frame_idx: 0, reg: 3 }
// After frame pop:   Upvalue::Closed { value: Smi(42) }
  // the closure still works — it reads from the upvalue, not the dead frame

The closing happens when a frame pops: scan all open upvalues, and for any that point into the popping frame, copy the value in and convert to Closed.

The upvalue becomes invalid and the closure crashes
The upvalue is deleted and the closure reads a default value
The upvalue copies the value from the register and becomes Closed
The parent frame is kept alive as long as the closure exists

Frames Reference Closures

The Frame no longer borrows &Program or clones a cons pool. It holds a Value pointing to a Closure on the heap: 

struct Frame {
    ip: usize,
    reg: [Value; 256],
    closure: Value,       // heap pointer to Closure
}

// Reading bytecode in the VM:
let closure = self.heap.read_closure(stack[fi].closure);
let function = self.heap.read_function(closure.function);
let opcode = function.code[stack[fi].ip];

// Loading a constant:
let idx = function.code[stack[fi].ip] as usize;
self.acc = function.cons[idx];

No &Program borrow. No cloned cons. The function and its constant pool live on the heap and the GC manages them. Fresh frames always read from the live heap object — never from a stale clone.

Compilation

The compiler’s job changes. Instead of building a Program struct, it allocates objects on the heap and returns a Value: 

impl Compiler {
    pub fn compile(
        &mut self,
        stmts: &[Stmt],
        heap: &mut Heap,
    ) -> Value {
        // 1. Compile bytecode into self.code, constants into self.cons
        for stmt in stmts {
            self.compile_stmt(stmt, heap);
        }

        // 2. Allocate the BytecodeFunction on the heap
        let func_val = heap.alloc(HeapObject::Function(
            BytecodeFunction {
                code: std::mem::take(&mut self.code),
                cons: std::mem::take(&mut self.cons),
                param_count: self.param_count,
                reg_count: self.next_reg,
            }
        ));

        // 3. Wrap in a Closure (no upvalues yet)
        heap.alloc(HeapObject::Closure(HeapClosure {
            function: func_val,
            upvalues: vec![],
        }))
    }
}

For FuncDecl, the child compiler recursively compiles the function body, allocates the child BytecodeFunction + Closure on the heap, and the parent stores the Closure Value in its constant pool — so the Call instruction can load it.

Implementation Steps

  1. Define HeapObject types — HeapString, BytecodeFunction, HeapClosure, the HeapObject enum
  2. Rewrite Heap — Vec<Option<HeapObject>> with alloc, read_string, read_function, read_closure
  3. Rewrite GC — recursive mark + sweep, no remap
  4. Change Frame — replace program: &Program and cons: Vec<Value> with closure: Value
  5. Change compiler — allocate BytecodeFunction and Closure on heap, return Value
  6. Change VM — read bytecode and constants through heap.read_closure / heap.read_function
  7. Update tests — significant refactor, since Program and Frame shapes change
This is a big refactor. Expect to touch every file. Start with the Heap restructure and get alloc/read_string working with existing tests. Then add Function/Closure types. Then change Frame and the VM. Keep tests green after each step — don’t try to change everything at once.
