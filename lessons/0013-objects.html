Objects — Property Maps on the Heap

Lesson 13 · ~45 min · Prev: Lesson 12 · Reference: Instruction Set

Until now, every value in your VM is either a number or a string. There are no compound data structures — no way to group related values together. In JavaScript, the answer is the object: a bag of named properties, each holding a Value.

This lesson adds a new heap type (JSObject), three new bytecodes (CreateObject, SetProperty, GetProperty), and the syntax for object literals and dot-access. It’s the biggest change since closures — and the foundation for everything that follows (arrays, classes, prototypes, this).

What an Object Is

At the language level, a JavaScript object is a collection of key–value pairs: 

let point = { x: 10, y: 20 };
point.x;       // 10
point.y = 30;  // update a property

At the VM level, an object is a heap-allocated map from strings to Values. When you write point.x, the VM looks up the string "x" in the object’s property map and returns the associated Value.

The New Heap Type: JSObject

use std::collections::HashMap;

pub struct JSObject {
    pub properties: HashMap<String, Value>,
}

pub enum HeapObject {
    String(HeapString),
    Function(BytecodeFunction),
    Closure(Closure),
    Object(JSObject),           // ← new
}

A HashMap<String, Value> is the simplest correct implementation. Each property name maps to a Value that can be a Smi, a heap pointer to a string, a closure, or even another object. The values are fully dynamic — any property can hold any type, and properties can be added at any time.

Why use a HashMap<String, Value> for object properties instead of a Vec<Value>?
Vec doesn’t support heap-allocated Values
Objects can only have string keys, so Vec is incompatible
Properties are accessed by name — a map gives O(1) lookup by key
HashMap is required by the JavaScript specification

Three New Bytecodes

Objects need three operations: create, read a property, write a property. Each gets a bytecode:

BytecodeValueOperandsEffect
CreateObject 22 none Allocate empty JSObject on heap, store in acc
SetProperty 23 [name_idx] [obj_reg] Set property constants[name_idx] on object in obj_reg to acc
GetProperty 24 [name_idx] [obj_reg] Load property constants[name_idx] from object in obj_reg into acc 
#[repr(u8)]
pub enum ByteCode {
    // ... existing opcodes 0–21 ...
    CreateObject = 22,
    SetProperty  = 23,
    GetProperty  = 24,
}

SetProperty and GetProperty take two operands: a constant pool index for the property name (a heap-allocated string), and a register holding the object reference. The property name is always a string in the constant pool — not a register, because property names are known at compile time.

New Tokens and AST

Lexer tokens

Object literals use : to separate keys from values. Property access uses . for dot notation: 

pub enum SymbolKind {
    // ... existing variants ...
    Dot,     // .
    Colon,   // :
}

AST nodes

pub enum Expr {
    // ... existing variants ...
    ObjectLit {
        properties: Vec<(String, Expr)>,
    },
    PropertyAccess {
        object: Box<Expr>,
        property: String,
    },
}

pub enum Stmt {
    // ... existing variants ...
    PropertyAssign {
        object: String,       // variable name holding the object
        property: String,     // property name
        value: Expr,          // value to assign
    },
}

PropertyAssign is simplified: the object is identified by a variable name (not an arbitrary expression). This means point.x = 10; works, but getObj().x = 10; doesn’t. This is a pragmatic limitation — supporting arbitrary left-hand-side expressions requires a more complex compilation strategy that can be added later.

Parsing Objects

Object literals

When the parser sees { at the start of an expression (inside parse_factor), it parses an object literal: 

SymbolKind::LBrace => {
    self.pop();  // consume {
    let mut properties = Vec::new();
    while self.peek() != SymbolKind::RBrace {
        let key = self.expect(SymbolKind::Ident).str_val;
        self.expect(SymbolKind::Colon);
        let value = self.parse_expr();
        properties.push((key, value));
        if self.peek() == SymbolKind::Comma {
            self.pop();
        }
    }
    self.expect(SymbolKind::RBrace);
    Expr::ObjectLit { properties }
}

Property access: dot notation

After parsing a primary expression like an identifier, check for a trailing .: 

// In parse_factor, after parsing an Ident:
SymbolKind::Ident => {
    let s = self.pop();
    if self.peek() == SymbolKind::LPar {
        // ... function call (existing) ...
    } else if self.peek() == SymbolKind::Dot {
        self.pop();  // consume .
        let property = self.expect(SymbolKind::Ident).str_val;
        Expr::PropertyAccess {
            object: Box::new(Expr::Ident(s.str_val)),
            property,
        }
    } else {
        Expr::Ident(s.str_val)
    }
}

Property assignment

In parse_expr_stmt, extend the lookahead to detect ident.ident = expr;: 

fn parse_expr_stmt(&mut self) -> Stmt {
    if self.peek() == SymbolKind::Ident {
        // Check for property assignment: obj.prop = expr;
        if self.pos + 2 < self.syms.len()
            && self.syms[self.pos + 1].kind == SymbolKind::Dot
            && self.syms[self.pos + 2].kind == SymbolKind::Ident
        {
            // Peek further: is there an = after the property name?
            if self.pos + 3 < self.syms.len()
                && self.syms[self.pos + 3].kind == SymbolKind::Assign
            {
                let object = self.pop().str_val;
                self.expect(SymbolKind::Dot);
                let property = self.expect(SymbolKind::Ident).str_val;
                self.expect(SymbolKind::Assign);
                let value = self.parse_expr();
                self.expect(SymbolKind::Semi);
                return Stmt::PropertyAssign { object, property, value };
            }
        }
        // ... existing assignment check ...
    }
    // ... existing expression statement ...
}

The lookahead checks four tokens ahead: ident . ident =. This distinguishes property assignment from property access used as an expression.

Compiling Object Literals

An object literal { x: 10, y: 20 } compiles to:

  1. Emit CreateObject — allocates an empty JSObject, result in acc.
  2. Store the object in a temp register.
  3. For each property: compile the value expression, emit SetProperty with the property name (from the constant pool) and the object register.
Expr::ObjectLit { properties } => {
    // 1. Create empty object
    self.code.push(ByteCode::CreateObject as u8);

    // 2. Store object reference in a temp register
    let obj_reg = self.alloc_reg();
    self.code.push(ByteCode::Star as u8);
    self.code.push(obj_reg as u8);

    // 3. For each property, compile value and set it
    for (key, value) in properties {
        self.compile_expr(value, heap);

        // Add property name string to constant pool
        let name_val = heap.alloc_string(key);
        let name_idx = self.constant_pool.len();
        self.constant_pool.push(name_val);

        self.code.push(ByteCode::SetProperty as u8);
        self.code.push(name_idx as u8);
        self.code.push(obj_reg as u8);
    }

    // 4. Leave the object in acc for the caller
    self.code.push(ByteCode::Ldar as u8);
    self.code.push(obj_reg as u8);
}

After compilation, the object sits in acc. If this is the right-hand side of let point = { ... };, the enclosing VarDecl will Star it into the variable’s register.

Compiling Property Access

Expr::PropertyAccess { object, property } => {
    // Compile the object expression (puts object ref in acc)
    self.compile_expr(object, heap);
    let obj_reg = self.alloc_reg();
    self.code.push(ByteCode::Star as u8);
    self.code.push(obj_reg as u8);

    // Property name goes in constant pool
    let name_val = heap.alloc_string(property);
    let name_idx = self.constant_pool.len();
    self.constant_pool.push(name_val);

    // Emit GetProperty
    self.code.push(ByteCode::GetProperty as u8);
    self.code.push(name_idx as u8);
    self.code.push(obj_reg as u8);
}

Compiling Property Assignment

Stmt::PropertyAssign { object, property, value } => {
    // Compile the value expression
    self.compile_expr(value, heap);

    // Look up the object's register
    let obj_reg = self.symbols[object];

    // Property name in constant pool
    let name_val = heap.alloc_string(property);
    let name_idx = self.constant_pool.len();
    self.constant_pool.push(name_val);

    // Emit SetProperty
    self.code.push(ByteCode::SetProperty as u8);
    self.code.push(name_idx as u8);
    self.code.push(obj_reg as u8);
}

VM Handlers

The Heap needs three new methods: 

impl Heap {
    pub fn read_object(&self, val: Value) -> &JSObject {
        match &self.objects[val.heap_offset()] {
            Some(HeapObject::Object(o)) => o,
            other => panic!("expected Object, got {:?}", other),
        }
    }

    pub fn get_property(&self, obj_val: Value, name: &str) -> Value {
        let obj = self.read_object(obj_val);
        *obj.properties.get(name)
            .unwrap_or_else(|| panic!("property '{}' not found", name))
    }

    pub fn set_property(&mut self, obj_val: Value, name: String, value: Value) {
        match &mut self.objects[obj_val.heap_offset()] {
            Some(HeapObject::Object(o)) => {
                o.properties.insert(name, value);
            }
            other => panic!("expected Object, got {:?}", other),
        }
    }
}

And the bytecode dispatch:

ByteCode::CreateObject => {
    self.acc = self.heap.alloc(HeapObject::Object(JSObject {
        properties: HashMap::new(),
    }));
}

ByteCode::SetProperty => {
    let name_idx = call_stack.frames[fi].read_byte() as usize;
    call_stack.frames[fi].pc += 1;
    let obj_reg = call_stack.frames[fi].read_byte() as usize;
    call_stack.frames[fi].pc += 1;

    let name_val = call_stack.frames[fi].read_constant(name_idx);
    let name = self.heap.read_string(name_val).to_string();
    let obj_val = call_stack.reg(fi, obj_reg);
    self.heap.set_property(obj_val, name, self.acc);
}

ByteCode::GetProperty => {
    let name_idx = call_stack.frames[fi].read_byte() as usize;
    call_stack.frames[fi].pc += 1;
    let obj_reg = call_stack.frames[fi].read_byte() as usize;
    call_stack.frames[fi].pc += 1;

    let name_val = call_stack.frames[fi].read_constant(name_idx);
    let name = self.heap.read_string(name_val);
    let obj_val = call_stack.reg(fi, obj_reg);
    self.acc = self.heap.get_property(obj_val, name);
}
What does CreateObject leave in the accumulator?
A Smi containing the object’s property count
A heap pointer (tagged Value) to the new empty JSObject
The object’s first property value
A constant pool index referencing the object

Worked Example

Source:

let point = { x: 10, y: 20 };
let sum = point.x + point.y;

Compiled bytecode:

addr  instruction             effect
————  —————————————————————  —————————————————————————
                               ; let point = { x: 10, y: 20 };
0000  CreateObject              acc = {} (empty JSObject on heap)
0001  Star r0                   r0 = acc  (temp: object ref)

0003  LdaSmi [0] (10)          acc = 10
0005  SetProperty [1] r0        point["x"] = 10  ([1] = "x" in constant pool)

0008  LdaSmi [2] (20)          acc = 20
0010  SetProperty [3] r0        point["y"] = 20  ([3] = "y" in constant pool)

0013  Ldar r0                   acc = point object
0015  Star r1                   r1 = point  (var declaration register)

                               ; let sum = point.x + point.y;
0017  Ldar r1                   acc = point
0019  Star r2                   r2 = point  (temp for GetProperty)
0021  GetProperty [1] r2        acc = point.x = 10

0024  Star r3                   r3 = 10  (stash for addition)

0026  Ldar r1                   acc = point
0028  Star r4                   r4 = point
0030  GetProperty [3] r4        acc = point.y = 20

0033  Add r3                    acc = 10 + 20 = 30
0035  Star r5                   r5 = 30  (let sum = 30)

Notice how property names "x" and "y" live in the constant pool as heap-allocated strings (indices [1] and [3]). The same constant pool index is reused when reading the property later — SetProperty [1] and GetProperty [1] both refer to "x".

GC: Tracing Through Objects

Objects contain Values that may be heap pointers — a property could hold a string, a closure, or another object. The garbage collector must trace into object properties: 

fn mark(&self, marked: &mut Vec<bool>, val: Value) {
    if !val.is_heap_object() { return; }
    let idx = val.heap_offset();
    if idx >= self.objects.len() || marked[idx] { return; }
    marked[idx] = true;

    match &self.objects[idx] {
        Some(HeapObject::String(_)) => {}
        Some(HeapObject::Function(f)) => {
            for &v in &f.constant_pool {
                self.mark(marked, v);
            }
        }
        Some(HeapObject::Closure(c)) => {
            self.mark(marked, c.function);
            for &v in &c.upvalues {
                self.mark(marked, v);
            }
        }
        Some(HeapObject::Object(o)) => {           // ← new
            for &v in o.properties.values() {
                self.mark(marked, v);
            }
        }
        None => {}
    }
}

Without this, any object held as a property value would be collected prematurely. Consider: 

let inner = { value: 42 };
let outer = { child: inner };
// inner is no longer in a register — only reachable through outer.child
// GC must trace: outer → properties → "child" → inner
An object outer has a property child pointing to another object inner. The variable inner is no longer in any register. How does the GC know inner is still alive?
It traces outer’s properties and follows the Value pointing to inner
The VM maintains a separate list of all objects
Objects are never garbage collected
inner is collected — this is a known limitation

How V8 Does It: Hidden Classes

Our HashMap<String, Value> is correct but slow. Every property access hashes the property name and probes the map. V8 solves this with hidden classes (internally called Maps): 

// Two objects with the same shape share one hidden class:
let a = { x: 1, y: 2 };  // hidden class: Map{ x: offset 0, y: offset 1 }
let b = { x: 3, y: 4 };  // same hidden class — shared!

// Property access compiles to a fixed offset:
// a.x → load a[offset 0]  (no hash lookup)

A hidden class is a property layout descriptor. It maps property names to fixed offsets in a dense array. Objects with the same set of properties in the same order share the same hidden class. Property access becomes an array index instead of a hash lookup.

Aspectg8 (HashMap)V8 (Hidden Classes)
Property storageHashMap<String, Value>Dense Vec<Value> + Map pointer
Property readHash lookup — O(1) averageFixed offset — O(1) worst case
Memory per objectHashMap overhead (~72 bytes empty)Values array + 1 pointer to Map
Shape sharingNone — each object owns its mapSame-shape objects share a Map
Inline cachesNoneIC caches the Map + offset for fast repeat access
Adding a propertyHashMap::insertTransition to a new Map (creates a transition tree)
V8 parallel: V8’s GetNamedProperty bytecode is our GetProperty. V8’s SetNamedProperty is our SetProperty. V8’s CreateObjectLiteral uses a boilerplate — a pre-built template object that gets shallow-cloned, avoiding the create-then-set-each-property dance. Our CreateObject + per-property SetProperty sequence is the naïve version.
Why does V8 use hidden classes instead of HashMaps for object properties?
HashMaps aren’t supported in C++
Hidden classes turn property access into a fixed-offset array read — faster and cache-friendly
Hidden classes use less memory by storing property names inline
The JavaScript spec requires hidden classes

Implementation Steps

  1. Lexer: Add Dot and Colon to SymbolKind. Recognize . and : in the lexer match.
  2. AST: Add Expr::ObjectLit, Expr::PropertyAccess, and Stmt::PropertyAssign. Add Display for each.
  3. Parser:
    • parse_factor: handle LBrace for object literals, and Dot after identifiers for property access.
    • parse_expr_stmt: detect ident.ident = expr; for property assignment (4-token lookahead).
  4. Bytecodes: Add CreateObject = 22, SetProperty = 23, GetProperty = 24 to the enum, From<u8>, and Display.
  5. Heap: Add JSObject struct and HeapObject::Object variant. Add read_object, get_property, set_property methods.
  6. Compiler:
    • ObjectLit: emit CreateObject, store in temp reg, compile each property value + SetProperty, reload object into acc.
    • PropertyAccess: compile object expr, store in temp reg, emit GetProperty.
    • PropertyAssign: compile value, look up object register, emit SetProperty.
  7. VM: Add handlers for the three new bytecodes.
  8. GC: Update mark to trace JSObject property values.
  9. Test: 
    let p = { x: 10, y: 20 }; p.x + p.y;
    → 30. 
    let p = { x: 1 }; p.x = 99; p.x;
    → 99.
Watch out for register allocation in object literals. Each SetProperty needs the object in a register, but compiling the property value may use the accumulator. Make sure you Star the object reference into a register before compiling property values, and reload it into acc at the end so the enclosing expression gets the object, not the last property value.

What This Unlocks

With objects, your VM can express:

  • Structured data: let user = { name: "alice", age: 30 };
  • Nested objects: let rect = { origin: { x: 0, y: 0 }, width: 100 };
  • Mutable state: point.x = point.x + 1;
  • Object-passing: pass objects to functions, return objects from functions

Still missing (future lessons):

  • Arrays: dense indexed collections — a specialized object with integer keys and length
  • Hidden classes: replace HashMap with offset-based property access for performance
  • Prototypes: prototype chains for method sharing and inheritance
  • this: method calls that bind the receiver object
  • Computed property access: obj[expr] instead of just obj.name
